# Dependency Policy

## Principles

ScolaOS keeps the mandatory runtime surface deliberately small. A dependency is accepted only when it materially improves correctness, security, maintainability, interoperability, or delivery speed compared with owning the capability directly.

## Admission checklist

Before adding a production dependency, review:

1. maintenance activity and ownership;
2. security/advisory history;
3. license compatibility with AGPL-3.0-only distribution;
4. transitive dependency cost;
5. runtime/bundle impact;
6. ability to self-host without a proprietary service;
7. replacement/exit path;
8. whether the capability belongs behind an adapter.

## Versioning

- Root toolchain dependencies are exact-pinned.
- Application dependencies should normally use exact versions until the first stable release process is proven.
- `pnpm-lock.yaml` is required in source control once generated by the approved toolchain.
- CI must switch to frozen-lockfile installation immediately after the lockfile is committed.
- Major updates are reviewed individually.
- Minor/patch development and production updates may be grouped separately by Dependabot.

## Current TypeScript pin

TypeScript is intentionally pinned to 6.0.x while the selected typescript-eslint line officially supports TypeScript `<6.1.0`. Upgrade to TypeScript 7 only after the linter/parser stack declares support and CI passes without suppressing unsupported-version diagnostics.

## Automated checks

- Dependabot: weekly npm and GitHub Actions version-update PRs.
- `pnpm audit --audit-level=high`: pull request, main push, and weekly workflow.
- GitHub public-repository secret scanning: relied on for repository secret detection; push protection should remain enabled in repository security settings.

Security alerts are triaged by exploitability, affected path, data exposure, and whether the dependency is present in a shipped runtime or development-only tooling.
