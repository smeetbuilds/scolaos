# Installer bootstrap domain and transaction foundation

**Date:** 14 August 2026  
**Status:** bootstrap/domain contract complete; PostgreSQL adapter and installer UI integration pending

This tranche defines the first-school bootstrap boundary that sits after database connectivity/migrations and before post-install verification. It intentionally does not claim that M1-032, M1-033 or M1-034 are database-complete.

## Scope

The bootstrap input covers the minimum coherent first institution:

- institution name, short code, country, timezone, currency, locale and week start;
- one active default branch/campus;
- one active initial academic session;
- one administrator identity with full name, email and password confirmation.

IDs are generated by trusted server/runtime code. Browser-supplied identifiers are not accepted as bootstrap entity identities.

## Domain normalization

`packages/domain/src/bootstrap.ts` reuses the institution/session invariants from `packages/domain/src/institution.ts` and adds installer-specific administrator normalization.

The initial branch is always active/default. The initial academic session is active. Administrator email preserves the delivery local-part spelling while normalizing the domain and creates a separate NFKC/lowercase login identifier.

Password confirmation is checked before persistence. The coordinator receives a password-hasher dependency; the production adapter must bind this to the accepted identity password implementation. The raw password and confirmation are never members of a persistence record or completion receipt.

## Transaction contract

`InstallerBootstrapCoordinator` requires one repository transaction for:

1. re-checking an existing bootstrap receipt;
2. applying the versioned seed plan;
3. creating the institution;
4. creating its default branch;
5. creating the active academic session;
6. creating the administrator user with only a password hash;
7. creating the administrator membership;
8. assigning the seeded `super-administrator` role for that institution;
9. recording the bootstrap receipt.

The repository contract is deliberately transaction-shaped. A PostgreSQL adapter must make this an actual database transaction; an adapter that performs the calls independently does not satisfy M1-034.

The coordinator performs a cheap receipt preflight and a second receipt check inside the transaction. This avoids expensive password hashing for ordinary completed replays while keeping concurrent retries safe at the transaction boundary.

A broken ID generator returning duplicate IDs is rejected before persistence. An empty/oversized password record or a hasher that returns the raw password is also rejected.

## Retry/idempotency semantics

A completed bootstrap is keyed by the installation ID. Replaying it returns the stored receipt instead of creating a second institution/admin.

A failed transaction must not expose a receipt or any partial committed school state. Real PostgreSQL constraints/transaction rollback are still required to prove this property end-to-end.

## Seed plan

`apps/server/src/installation/seed-plan.ts` binds installation seeding to the current first-party permission catalog and default-role templates.

The plan validates:

- no duplicate permission IDs;
- no duplicate role keys;
- no role references an unknown permission;
- no role repeats a permission;
- a `super-administrator` template exists;
- that template explicitly contains every current permission.

The plan has three explicit versions:

- system seed version;
- permission catalog version;
- default role-template version.

It also calculates a deterministic SHA-256 fingerprint over the exact catalog/template payload. The bootstrap receipt carries the versions plus this fingerprint so a future post-install verifier/upgrade path can detect seeded-content drift that version numbers alone would miss.

## Security properties

- raw administrator password is ephemeral and never passed to the persistence transaction;
- password confirmation never reaches persistence;
- first admin privilege comes from an explicit seeded role assignment, not a hard-coded runtime role-name bypass;
- every current permission must be explicitly present in the super-administrator seed template;
- generated identifiers must be unique;
- retry uses a durable installation receipt rather than duplicate creation;
- transaction failure must roll back institution/branch/session/user/membership/role/receipt together;
- seed fingerprint is integrity metadata, not a secret or authorization credential.

## Executed evidence in this environment

The dependency-independent implementation was strict-typechecked with global TypeScript 5.8.3. A real Node harness executed the coordinator and seed-plan behavior and passed:

```text
installer-bootstrap-harness: PASS
seed-plan-harness: PASS
```

The harness covered normalization, full write order, password-hash-only persistence, completed replay behavior without a second hash/ID allocation, transaction failure rollback semantics in a transactional fake, duplicate generated-ID rejection, raw-password-hasher rejection, seed validation and deterministic seed fingerprinting.

- `packages/domain/src/bootstrap.test.ts`;
